# 博主网络：让下一次学习用上这一次的积累

日期：2026-09-06。状态：**用户已认可，正在按最新找人请教目标实施**。最新执行合同见 agent-specs.md 第五节，验收见 as-implemented-logic.md。作者、问题和数字示例均为说明规则，不是真实效果测量。

## 1. 建议的定位

博主网络保存的是：**哪些作者的哪些材料，曾经在什么问题上帮助过我，以及我怎样把它们变成了自己的理解。**

用户能得到三个直接结果：下次更容易找到适合自己的讲解；随时找回一个认识的来源；在熟悉的解释之外找到有依据的新视角。网络页面是这些积累的入口，主要收益应出现在研究、知识脉络和聊天里。

面向用户的一句话可以是：**记住帮你理解问题的人，也帮你找到下一位。** 界面继续叫“博主网络”，副标题用“你的学习来源与使用足迹”。“联系”“问过的”“信任度”容易被理解为真实社交关系或正确性保证，建议换成“读过”“采用过”“你标记有帮助”。

如果上线后，它只能显示更多节点、更多连线，而不能改善后续找资料和理解问题的过程，这项功能就没有证明自己的价值。

## 2. 当前为什么感受不到作用

依据本次现场源码，而不是旧页面或旧算法文档：

| 当前实现 | 用户感受到的缺口 |
| --- | --- |
| `server/durable/flows.ts` 首次学习保存文章、生成回答，但不把文章作者写入网络 | 学了很多内容，网络仍可能是空的 |
| 问博主结果写 high，搜索博主结果写 low；数据库只接受这两档 | 权重表示入口来源，无法表达是否真的帮到了用户 |
| 普通 AI 回复不更新作者使用记录 | 已有的卡片延展行为没有转化为下一次学习的积累 |
| `network-retrieval.ts` 在旧问题和标题上做词项匹配，高权优先，够三人即停止 | 对换个问法、换个应用场景不够敏感，也缺少新观点入口 |
| `src/learning-v2/Authors.tsx` 展示作者、文章标题、来源档位和原文链接 | 很难知道为什么推荐此人、和自己的哪次学习有关 |
| 研究/聊天材料范围目前不读取作者网络 | 除了搜索博主，积累没有回到核心学习过程 |

现有机制有复用资料的基础，但不是已完成的个性化推荐系统，也不是社会关系网络。部分 API 条目缺少稳定作者 ID，代码会使用与证据绑定的后备 ID；跨文章识别同一个人仍需解决，不能按姓名直接合并。

## 3. 网络里需要保存什么

最小闭环是“作者 → 文章 → 我的知识卡 → 我的使用/反馈”。概念标签把这些关系组织起来。

| 对象 | 需要记录 | 能回答的问题 |
| --- | --- | --- |
| 作者 | 稳定平台身份、展示名、身份是否已确认 | 这几篇文章是否确实属于同一个人？ |
| 来源材料 | 真实链接、证据 ID、完整 API 总结、检索时间、内容版本 | 当时读的是什么，依据在哪里？ |
| 学习主题 | 当前概念、所属路线；跨路线同义概念的映射单独管理 | 他在哪个主题上对我有用？ |
| 使用足迹 | 用户提问、直接依据卡、对应来源、生成批次、保留/删除/反馈 | 哪张卡从这篇文章延伸出来？ |
| 我的偏好 | 在某主题上的使用次数、有帮助反馈、少推荐/固定选择 | 下次同类问题怎样选材更适合我？ |

**作者网络与知识树分开存放。** 知识树依然是一张卡只有一个父卡；同一作者参与多个概念，通过作者页的反向索引展示，不在知识画布中添加跨树汇合线。作者之间也不能因为都被用户读过，就画成真实社交关系。

## 4. 什么时候入网

1. 首次三路概念搜索收齐并筛选后，所有被接纳文章的可识别作者自动记为“发现过”。不多弹一次确认，也不自动关注知乎账号。
2. 用户在某篇文章或其后续卡片上发起问题，形成有效的主动使用足迹。
3. 用户明确点“有帮助”，才形成正面的效果反馈；“收藏作者/优先参考”是用户直接设置的偏好。
4. 问博主找到的 1–3 位新作者以及独立搜索博主的结果，也进入同一份来源资料库。
5. 作者不明的文章仍可学习，但归入“作者待确认”，不编造身份、不借展示名并入其他人。

自动入网仅代表系统保存了来源。首次 AI 自动生成十张卡，不代表用户十次认可了作者。自动推荐、自动引用也都不应自我增加作者偏好。

## 5. “延伸卡片 +1”怎么设计才有意义

建议把权重显示为两个容易理解的东西：**主动使用记录**和**有帮助反馈**。内部另算排序所用的主题偏好，不给博主贴一个全局“专业度 87 分”。

| 行为 | 记录和推荐作用 |
| --- | --- |
| 搜索命中、自动加入文章列表 | 记录发现，偏好不加分 |
| 首次 AI 自动讲解、自动长卡 | 记录来源关系，偏好不加分 |
| 仅打开文章 | 记录看过，不推断喜欢或读懂 |
| 用户主动基于文章发起一次有效追问 | 本主题主动使用 +1；作为弱偏好 |
| 同一问题生成 8 段、任务重试、刷新补发 | 仍只记这一次，不按生成卡数计数 |
| 用户再点“解释一下” | 是新的使用，但可能意味着没读懂；不能等同“有帮助” |
| 明确“有帮助” | 独立正反馈；对同一结果只能生效一次，可撤销 |
| “暂时看不懂” | 调整难度/讲法匹配，不给作者扣正确性分 |
| “不相关” | 降低本主题推荐，不影响其他主题 |
| “内容有问题” | 针对这份材料标记，不把一个来源的错误扩大为整个人不可信 |
| 少推荐/不再推荐/优先参考 | 可解释、可撤销的用户控制；优先参考也不能突破材料相关性 |

首版的数值建议仅作为可调试起点：一次主动使用贡献 1，明确有帮助贡献 2；同一作者同一主题同一天的隐式使用贡献最多 3，显式选择单独保留。排序贡献封顶，不能靠反复点击无限上升。最近使用对近期排序更有影响，历史足迹仍保留。具体系数要通过实际反馈评估，不作为产品质量定律。

**归因边界：**

- 沿卡片唯一父链找到对应来源；自定义卡且没有可追溯来源时不归给任何作者。
- 一次多选提问，如果用户未指定单一依据，只记录实际被引用的材料。隐式偏好总增量最多 1，在被引用的不同来源作者之间分配；“默认全部”本身不构成用户偏好，首次回答完全不计。
- 在 AI 子卡上继续提问，足迹可追溯到原文，但使用信用不能随 AI 自动链条倍增。
- 同一作者的三篇文章仍是一个作者；证据数量和使用次数分开。
- 删除/撤销生成分支后，活动卡计数回退；原始“曾经主动使用”事件可保留为历史，但不继续滚动加分。移除学习内容/清除个性化数据时同步清理对应索引和偏好。

所以 +1 的意义是：“下一次相关问题，我有一点理由更早让你看这位作者的合适材料。”它不是奖励作者流量、评价学术水平，或证明这段讲解正确。

## 6. 有网络和没有网络的区别，必须在结果上看得见

仍然先判断**这篇材料能否支持本次问题**，再考虑对这个用户是否有用。历史偏好不能把不相关的人推到前面。

| 同一个问题 | 不使用学习积累 | 使用学习积累后的设计 |
| --- | --- | --- |
| 为什么换一组基，矩阵会变？ | 按当前检索材料相关性选作者 | 在相关材料里优先展示用户之前标记有帮助的几何讲法，并显示当时采用的知识卡 |
| 推荐机器学习优化方向的博主 | 从当前结果寻找相关作者 | 代数主题的高使用权重不会直接迁移到优化；仍须有优化主题的真实材料 |
| 想看与当前文章不同的解释 | 重新找相关材料 | 排除当前概念已出现的作者，结合已有内容识别缺的讲法，找 1–3 位新作者 |
| 想找回以前理解过的例子 | 依靠用户记住关键词或作者 | 可直接沿“概念 → 当时的问题 → 有帮助的文章 → 我的卡片”回去 |

一张推荐结果至少包含：作者、当前问题对应的文章、为什么相关、与我的哪次学习有关、原文，以及“加入本次学习”。例如：“你在‘向量空间’里把他的几何例子标为有帮助；这篇材料具体解释换基。”没有这条真实历史，就只显示“本次新发现”。

建议提供轻量的“使用我的学习积累”开关。关闭时不使用偏好加权；评估时还能在相同候选材料上对照排序。不要虚构“提升 40%”或“为你节省 20 分钟”。

### 搜索策略建议

现行规则是高权 → 低权 → 不足三人才查知乎。下一版建议改为：先查积累，快速给出有依据的已有候选，再寻找互补的外部候选；最终最多三人。通常争取“熟悉的有效来源 + 一个有价值的新视角”，但没有相关新来源时不凑名额。

若已有三位都很好，用户仍应能看“换个新视角”，而不是被历史结果封闭住。本次用户认可后已同步修改 N0/N1/N2 合同，实施不再沿用“够三人就停止”。

推荐研究将准确性、多样性、新颖性和意外但有用的发现分别考察；这支持保留探索入口，但不能直接证明 ThreadPeak 的某个配比有效。[Google Research：Values of Exploration in Recommender Systems](https://research.google/pubs/values-of-exploration-in-recommender-systems/)

## 7. 怎么反馈到开始学习后的页面

### 7.1 研究：更快识别合适资料

首次学习仍执行三路、限定当前概念的知乎搜索，不能为了优先熟悉作者漏掉其他相关材料。结果收齐后去重筛选；在“最相关”排序下，同等相关材料可考虑主题偏好，“点赞最多”仍严格按真实点赞排序。

文章卡只增加有依据的轻量标签，如“你采用过”“几何例子”“同一作者的相关讲解”。标签不能代替内容总结。点击作者头像打开其主题与使用足迹；可以从那里找到其他文章，但**其他文章要先明确加入当前学习，才可作为本轮新依据**。

首次回答仍阅读当前全部材料，按各篇的实际贡献综合；不会因为某位作者权重高而只引用他，也不会规定每人必须分配一段。

### 7.2 知识脉络：知道自己的理解从哪里来

建议增加三类从作者入口触发的操作：

- **查看他帮我形成的卡片**：临时突出这些卡片及所在分支，其他卡片淡化；退出后恢复画布。不给原节点永久改色，不新增跨父连线。
- **补一个不同讲法**：对选中卡沿用“问博主”，查公开材料，找当前概念尚未出现的 1–3 位作者。每位作者卡仍直接接在所选卡后。
- **把这篇资料加入学习**：用户从作者页主动加入的新文章，作为当前概念根下的文章卡；后续 AI 段落各接在各自依据卡后。

这两种新增位置不能混淆：“问博主”是在选中卡后补充观点；“加入文章”是补充当前概念的来源材料。新证据保留真实作者/链接元数据，不因为放在所选卡后就声称它来自原卡作者。

跨主题回顾时，作者页可以展示“他在两个概念里都帮到你了”，点击跳到对应学习页与节点。这个关系存在于作者索引中，不把两棵知识树合并成一张多父图。

### 7.3 对话：材料可控，讲法可以逐步贴合用户

优先级固定为：当前问题与明确选卡 → 当前概念资料 → 本次对话 → 用户允许使用的学习偏好。权重属于选材提示，不能作为事实依据。

默认对话仍只使用当前学习的合法材料。作者网络不会偷偷把外部文章全文、别的概念聊天或个人资料塞进上下文。它可以在回答之外给出“你以前觉得这位作者的几何解释有帮助，要加入这篇相关材料吗？”这类可操作建议；用户点击后才扩展材料范围。

可复用的偏好记忆是“这个主题的几何例子曾获有帮助反馈”，带对应事件和版本；不能无依据总结成“用户数学能力差”。讲法偏好可以影响例子的形式，不能改变事实、跳过来源验证或冒用作者口吻。

问 AI 继续使用 `read_card_scope` / `append_cards`：每个段落一张依据卡，一个父节点。比较两位作者时，拆成分别引用各自材料的段落，通过并置阅读或对照视图表达差异，不生成两卡汇入一卡。

### 7.4 问博主：保留找新作者的意义

这里仍是寻找公开文章中已有的观点，不发消息、不假装博主本人实时回答。

“新”建议明确为**在当前概念学习中还没有出现**。他可能在用户其他主题的网络中，但当前概念中已有的作者仍排除。网络可以帮助识别缺少的讲法和查询方向，实际选入的证据仍须满足当前问题、当前排除集合及 API 身份回查。只有正常没有合适候选时才由刘看山补充，检索故障不能伪装成零位作者。

## 8. 用户的一次完整体验

1. 开始学“线性映射”，三路搜索得到相关文章，作者自然进入“发现过”。此时没有任何人被系统认定为用户喜欢。
2. 用户读甲的几何说明，基于文章问“为什么换基后坐标变了？”。生成三段，甲在此主题记录一次主动使用。
3. 用户给其中一段点“有帮助”，后续同类概念可优先展示甲的相关讲解。网络页能打开这次问题、原文与卡片。
4. 用户进入矩阵表示，搜索结果中甲的一篇材料确实相关，于是显示“你采用过这位作者的几何讲法”。这不是凭姓名硬塞文章。
5. 用户想听其他解释，点“问博主”。系统排除当前概念已有作者，找到乙的代数讲解，直接在选中卡后长乙的卡。
6. 用户分别追问甲、乙的材料，知识树保持单父；作者页可以回顾两种讲法分别帮用户形成了哪些理解。
7. 一周后用户问“我当时怎么理解换基的？”，从自己的卡片及来源找回那次讲解。这里才体现长期积累的价值。

## 9. 博主网络页面建议

保留现有“搜索博主 / 博主网络”两页结构，优先改内容与操作。

**搜索博主页：** 输入问题后，主区展示最多三位有真实材料支持的候选；结果区可看“为什么适合这个问题”“与你的哪次学习有关”“不同讲法”。每项支持读原文、查看足迹、加入当前学习。没有当前学习时先选已有概念；不能把文章塞到不相关概念里。

**博主网络页：** 默认从“当前主题”“经常采用”“最近有帮助”组织作者列表；网络图作为可切换的关系视图。新用户显示已收集文章的来源作者，不要求先专门搜索博主。没有材料时引导去学习，不伪造网络。

**作者详情：** 头像、真实身份信息、与哪些主题有关、已读文章、主动使用与有帮助记录、对应知识卡、我的偏好设置。身份不完整就标注，而不是把名字当作已确认身份。使用计数点击后能看到来源记录。

权重变化无需每次弹“+1”，可以在作者详情显示“已在这个主题采用 3 次”。界面重点展示可以继续做的事，少做排行榜和巨型关系图。

## 10. 商业价值与收费方式

最值得验证的付费价值是：**跨多次学习保留理解方式和来源，让持续学习减少重复找资料、重新理解和重新整理的成本。**

| 受益方 | 实际价值 | 建议阶段 |
| --- | --- | --- |
| 个人学习者 | 主题来源积累、跨概念回顾、适合自己的讲法、不同观点比较 | 首先验证；与学习产品订阅一起提供 |
| 深度学习用户 | 更大资料范围、更多跨主题整理、带来源的复习包、用户选择的更新检查 | 真实留存和使用反馈出现后再做付费分层 |
| 内容作者 | 有出处的有效阅读回流，知道自己的哪些材料帮助理解哪些问题 | 后续作者自愿认领后评估；不伪造合作或发送通知 |
| 团队/课程 | 共同整理的主题来源库、来源审核与教学资料复用 | 更后阶段，另立共享权限与内容授权合同 |

基础出处、引用准确性、偏好撤销不应成为付费门槛。收费可以围绕持续整理能力、规模与服务成本；先测愿意持续用和愿意付费，再讨论价格。

暂不建议靠“提高作者权重”卖推广位，否则用户会分不清推荐因为有帮助还是因为付了钱。未来若有作者课程、咨询或订阅合作，必须有真实身份、供给和授权，独立标明商业关系，不能把推广费混入个人帮助记录。

它的潜在竞争力来自“我在哪种问题上用过哪份资料、形成了怎样的理解”的可追溯积累，以及把积累带回任务的体验。单纯作者收藏、计数或图谱布局很容易复制。让用户能导出自己的资料和使用记录，也有助于建立信任；不要依靠锁住数据制造价值。

以上是商业假设，不是已验证的收入预测，也不宣称现有工具都没有类似功能。

## 11. 如何证明网络真的有用

做两类对照，不能把个性化排序的效果与多搜了材料的效果混在一起。

1. **同一候选集对照**：同一问题、同一模型与材料，关闭/开启主题积累，比较前几项的相关性、用户选择和有帮助反馈。第一阶段可由用户盲评两组顺序。
2. **完整流程对照**：允许加入历史来源后，比较找到第一份有用资料所需时间、重复检索次数、回答有帮助比例、跨周再次使用及成本。记录材料数量与来源，以解释差异。

核心指标建议是“从已有积累找到可用资料并完成一次有帮助学习的会话比例”，同时看原文/知识卡能否正确定位、错误引用率、主题相关性、新作者采用率和取消率。只看停留时间、作者数量、生成卡数，可能奖励用户困惑或无效生成。

新用户、熟悉主题、新主题应分开看。一个作者在代数上有帮助，不意味着在优化主题也有帮助。几何讲法的持续偏好也不能阻止用户看到严谨证明。

推出前先定义统计口径、实验分组和观察期。效果门槛用试点基线确定；这个文档不填造成功率、节省时间或转化率。

## 12. 后端怎样落地，保持现有可靠性约束

不用把所有模型调用强行改成 MCP。保留服务端固定流程，用小而可校验的工具读写对象即可。

| 能力边界 | 输入与输出约束 |
| --- | --- |
| 记录来源 | 当前所有者、真实证据 ID、已提交文章/作者身份；不由模型生成来源 ID |
| 记录使用 | 已接受的用户命令、已提交卡片与依据版本；重试只算一次 |
| 读取主题作者 | 当前概念/问题、用户偏好、排除作者；返回能回查的候选证据及推荐原因 |
| 加入学习 | 用户选中的真实来源、目标概念、去重与相关性检查；提交后才进入材料范围 |
| 读取回答范围 | 沿用 read_card_scope；作者偏好与内容证据分别标记 |
| 生成回答/卡片 | 沿用 append_cards；每操作一段、一个依据，不由网络权重决定父节点 |

文章事实、卡片、对话和来源关系仍在有所有者/版本检查的事务中提交；派生的使用计数、排序索引可以由事务 outbox 异步更新，失败后重放，不阻塞用户读取已发布内容。UI 可以继续使用上一版有效索引，不能把索引不可用说成“没有博主”。

使用事件的幂等键包括用户、命令/结果、事件类型和对应依据；保存权重计算版本，支持撤销与重算。模型不自由改权重。任务取消、失败、重试不额外加分。作者身份未知、文章删除、同一材料多次搜索都要有明确归并规则。

上下文先固定当前材料版本，再读取相关的少量偏好与可追溯历史；不能将整个作者网络全文加入每次回答。长来源按现有预算合同压缩，保留作者/证据/节点绑定；用户当前问题、显式选择和来源原文不被偏好摘要覆盖。没有足够证据时不推荐，也不加一个新的 Judge 替固定流程兜底。

首版可以先使用主题标签、关键词与现有同 Agent 的证据筛选。验证词项召回不足后再增加向量检索，不把引入图数据库、向量库或 MCP 当作价值实现本身。

## 13. 实施顺序与迁移

**第一步：让已有学习沉淀。** 首次文章作者入网，作者详情能反查原文与知识卡；加入一次有效主动使用记录和可撤销“有帮助”。先不改变排序，核对数据。

**第二步：让用户看见收益。** 搜索结果显示真实推荐原因与历史足迹；研究页作者入口和“加入本次学习”闭环；支持不使用个人积累的对照。更新对应 N0/N1/N2 合同。

**第三步：反哺学习。** 作者筛选知识卡、回顾自己的讲解、补不同观点；保持单父树、显式选卡和新对话边界。通过实际比较验证检索与回答收益。

**第四步：验证商业。** 先确定重复使用、跨周回顾和有帮助反馈，再试付费持续整理。授权作者服务、团队共享与内容更新提醒另行设计，不在第一版堆入。

迁移旧 high/low 时，只恢复“从问博主发现/从搜索发现”的来源事件，**不能把旧 high 直接转换为用户有帮助反馈**。已有学习文章可以补入为“历史来源”，初始主动使用与有帮助计数为零。身份待确认的记录不跨文合并。旧展示名保留为显示字段。

## 14. 参考与判断边界

Google 的来源发现说明展示了从检索、导入资料到继续问答与引用的闭环；可以借鉴“材料留在工作空间继续使用”的做法，不由此推断作者权重有效。[NotebookLM 来源发现说明](https://blog.google/innovation-and-ai/models-and-research/google-labs/notebooklm-discover-sources/)

当前官方笔记产品帮助页说明了来源生成思维导图，以及选中节点继续提问的交互。ThreadPeak 已采用的单父卡片树仍遵循自己的合同，不照搬其数据结构。[官方思维导图交互说明](https://support.google.com/gemininotebook/answer/16212283?hl=en)

这些来源支持资料复用、交互式探索和推荐多样性的设计方向；具体 UI、事件计分、排序、收费与实施节奏是本项目建议，需要试点验证。

## 15. AI 解不出来之后，把问题交给合适的人

核心故事：先用 AI 和公开资料理解问题；仍卡住时带着自己的学习上下文找人；通过他的真实文章判断值得问什么；整理简报后由用户去知乎邀请回答或确认付费咨询；用户的使用和有帮助反馈，帮助下一次从相关证据中选出更适合自己的作者。产品出售的价值是找人决策与问题准备的效率，而不是作者承诺、专家认证或咨询交易。订阅与留存仍需实测，不能将探索权重转成广告排名。

知乎官方[付费咨询说明](https://www.zhihu.com/consult/help)显示咨询由作者侧开关及入口控制。因此只有检索到相关文章，不能声称作者现在提供付费服务；先核实服务范围，再决定是否咨询。页面保留网络图谱原有视觉，最终搜索界面复用知识脉络与路线规划的共用页面组件；具体调整见第 16 节。

## 17. 本轮实现与验收记录

2026-09-06，本地默认服务与实际页面已接入本设计的首轮闭环。第 1–14 节中的未来商业、更新监控、团队及复习提案仍是后续探索，不表示已经实现。

- **搜索**：N0 先读取个人来源，再两路搜索；N2 选择 E/P 材料段落编号，程序取回引用，避免模型抄长引文造成持续修复。最多选 12 份相关材料，再按稳定作者 ID 编译为最多 3 位；同作者的其他相关材料保留在详情中。
- **关系**：每个作者保留多个证据，每份证据保留多个主题、搜索及问题关联。已归档对话仍可回查现存知识卡；删除卡不留下失效回链。数据库新增按搜索 ID 区分发现关系的迁移，避免同作者同文章再次搜索覆盖旧问题。
- **偏好**：显式选卡追问成功提交才产生一次使用事件，同命令不同作者分摊；按主题日封顶 3、累计弱偏好封顶 12，有帮助材料每份 2、总计封顶 12，可撤销。固定主题优先，独立问题仅借用本次相同文章的已有主题足迹，没有全局作者权威分。
- **请教**：人物卡展示切入点、原文、引用依据与待确认范围；抽屉中可编辑、复制简报，草稿在当前浏览器会话按搜索/作者保存。用户自行去知乎确认服务或邀请，没有发送/预约/支付功能。
- **回到学习**：相关材料经 L-source-select 校验后加入根下文章卡；从详情定位卡片，继续提问仍使用原有单父引用工具。作者图谱和知识树是不同的数据结构，前者允许多重关系，后者每卡唯一父节点。

本次浏览器与真实 provider 验证：

1. 基变换问题返回三位有公开材料依据的人选；一次有效真实搜索从首次拆问到完成，后续刷新恢复同一结果。
2. 请教简报可编辑和复制；关闭重开保留编辑值；未向任何作者发送内容。
3. 同一候选集，“mzhg”的相关材料标记有帮助后，在同等直接相关人选内提前；关闭积累排序后恢复普通顺序。测试反馈随后撤销，没有修改原始文章。
4. 一份换基材料被判为偏离“矩阵的运算”而未导入；图解矩阵乘法材料成功加入。随后引用该材料完成真实回答，增加一张唯一父卡，作者“遇见数学”显示主动使用 1 次、两个主题及对应问题和卡片回链。
5. 搜索、人物详情、网络图、反馈与学习跳转已实际操作。原 SVG 网络配色、点线、拖动/缩放实现未重新设计；页面容器不存在横向溢出。

自动化测试含新增作者模块 10 项，覆盖多文章/多问题/多主题、完整材料分段、压缩编号绑定、身份去重、不相关过滤、所有者边界、重复请求固定原上下文、取消/事务回滚与反馈撤销。本次 `npm test` 411 项通过，其中包含历史模块/替身测试，不能把每项都当作真实 provider 验收。构建仍有既存主包体积提示。更完整的生产身份、PostgreSQL 多进程、正式负载、真实匹配质量和稳定作者身份覆盖率，不由这些本地结果证明。

## 18. 作者页面滚动修复与补充验收（2026-09-06）

用户发现网络页面下半部被裁切，无法向下滚动。此前第 17 节的横向尺寸检查和点击定位没有覆盖真实滚轮，这是验收遗漏。

现场复现：工作区对直属 `main` 的 `overflow:hidden` 覆盖了市场页面的 `overflow:auto`。页面可视高度 590px、内容高度 1142px，普通滚轮操作后 `scrollTop` 仍为 0。图谱同时无条件阻止滚轮默认行为，把翻页变成了缩放。

修复为作者 `main` 独立纵向滚动，保留工作区裁切边界；预留滚动条位置，避免内容宽度跳变。桌面图谱高度随窗口调整，窄屏图谱与作者列表上下排列。普通滚轮交给页面；Ctrl / ⌘ + 滚轮用于图谱缩放，拖动交互保留，画布底部同步说明。页面支持键盘聚焦，焦点用中性灰色边界提示。

通过真实浏览器滚动操作补验，未通过脚本设置 `scrollTop`：

- 搜索页滚到 `scrollTop=1429` 的底部，看到了最后一位候选的“准备请教”和“继续寻找新作者”。
- 1280×720 网络页滚到最大值 454；指针位于图谱内向上滚动后降到 166，SVG 仍保持 `translate(0 0) scale(1)`，没有误缩放。
- 46 条作者列表滚到最大值 3939，最后一条作者及底部说明完整可见。
- 760×480 窗口页面滚到最大值 760，网络区域底边为 409px；详情抽屉滚到最大值 975，底部导入操作位于窗口内。
- 390×640 窗口，页面及网络容器 `scrollWidth` 与 `clientWidth` 相等，列表最末记录与底部说明可见。页面 Home 键回到顶部。测试后恢复原窗口尺寸。
