# ThreadPeak 前端、后端与 AI 后端审查

审查日期：2026-09-08。源码基线：`main` / `2b50e48`；执行环境：Node.js `v25.5.0`。本次继续 `ai.json` 中尚未形成最终结论的项目审查。历史对话仅用于恢复任务范围，结论以当前源码、产品裁决和本次执行证据为准。

**结论：确认 6 处行为问题，其中 3 项 P1、3 项 P2；另列出 8 组优化建议。优先修正 AI 输出的成功判定和资料恢复，再处理检索与大树性能。** 当前服务端已经具备持久任务、所有者隔离、检查点和共享限流等基础，问题集中在若干边界与合同不一致，并不需要重新引入一套 Agent 编排框架。

P1 表示应优先修复的结果正确性或用户选择丢失问题；P2 表示特定输入或数据规模下的功能问题。这是本次修复排序，不是安全漏洞评级。报告与复现材料已经完成，业务修复尚未实施。

## 2. 确认的问题

| 编号 | 优先级 | 触发与结果 | 验证方式 |
| --- | --- | --- | --- |
| F01 | P1 | R4 返回空对象或非 JSON，程序仍自行补路线并发布，还能构造无关资料锚点 | 真实持久 flow + 合成模型边界 |
| F02 | P1 | 正式 content 为空、reasoning 含 JSON，结构化 adapter 判为 completed | 真实 provider adapter + 合成 HTTP 响应 |
| F03 | P1 | 首页恢复资料请求暂时失败，原选择 ID 被覆盖为空且允许发送 | 真实 useMaterials hook + 临时网络错误 |
| F04 | P2 | 全网两篇文章仅查询参数不同，被视作同一 URL 丢掉一篇 | 真实搜索合并函数 + 合成检索结果 |
| F05 | P2 | 作者三条问法通过校验，实际发送时换了分组，产生 301 字查询 | 真实 learning.author flow + 搜索边界记录 |
| F06 | P2 | 合法深层单父树通过合同校验，布局时发生栈溢出 | 真实 validateTree + layoutTree |

### F01 · 无效 R4 被程序补成成功路线

位置：[tools.ts](../server/durable/tools.ts) L143–160；[staged-plan.ts](../server/path-generation/staged-plan.ts) 的 `conceptFrom`、`planFromExploration`、`salvageGoalPlan`；[flows.ts](../server/durable/flows.ts) 的路线发布分支。

`routePlan` 在结构校验失败时立即调用 `salvageGoalPlan`。三次结构修复仍失败时，又捕获 `STRUCTURE_NOT_SETTLED`，从 R2 探索候选生成计划并继续编译。修复器还会补概念、用途、学习深度、成功标准；缺少材料锚点时取第一份文件的文本片段，添加固定的关联说明。部分不合格结构被删边、裁剪或替换。

这超出了确定性编译应承担的 ID、结构转换和布局职责。当前合同要求新计划缺字段时由同一个 Agent 在相同提示词与深度下修复，不能借读取旧计划的兼容逻辑构造新的成功结果。

本次合成目标是“学习矩阵变换”，附件是明确无关的园艺资料。真实工作流的结果如下：

| R4 正式输出 | 模型调用次数 | 路线 / 任务状态 | 最终材料锚点 |
| --- | --- | --- | --- |
| `{}` | 1 | `published` / `completed` | 园艺原文，`role=direct`，关联说明“用这份资料理解本概念” |
| `this is not JSON` | 3 | `published` / `completed` | 同上 |

因此，格式错误不仅会被隐藏，还可能让无关来源看起来已经支持概念。ID 存在、引文确实来自原文以及 3D 校验通过，都不足以发现这种程序制造的语义关联。

修复建议：新生成路径只接受严格校验后的模型计划；保留受限的同 Agent 修复，耗尽后进入可检查的失败/等待状态并保存输入。历史兼容若仍有必要，应限制在旧记录读取入口。补齐“空对象、错误 JSON、缺 goalAlignment、无关材料、不存在的引用”拒绝发布测试。

现有 [goal-agents.test.mjs](../server/durable/goal-agents.test.mjs) 的 `routePlan salvages dumped R4 JSON instead of failing the path` 和 [staged-plan.test.mjs](../server/path-generation/staged-plan.test.mjs) 的相关断言认可了该行为，需要随修复一起调整，而不是据其通过判定合同成立。

### F02 · reasoning 中的 JSON 被当成正式答案

位置：[llm-provider.ts](../server/agent-runtime/llm-provider.ts) L47–48、L79–104；[schemas.ts](../server/agent-runtime/schemas.ts) 的 `extractStructuredJson`。

JSON 模式的完成判定允许 `reasoning` 代替空 `content`，随后将两者一并送入结构提取。非流式与流式路径都有这一入口。本次响应的 `finish_reason=stop`、`content=''`，只有 `reasoning_content` 含选择 JSON，真实 adapter 仍返回 `kind=completed` 和解析后的内容。

这是正式输出缺失仍被视作成功的问题。不是任意思考文字都能通过：它需要能提取 JSON，调用方也可能继续做 schema 检查；但符合 schema 的中间思考仍有机会成为正式结果。现有 [durable.test.mjs](../server/durable/durable.test.mjs) 的 `json completions recover the route object from reasoning when content is empty` 恰好固定了这条错误边界。

修复建议：结构化成功必须基于非空正式输出和完整结束信号；reasoning 仅用于诊断，不参与业务 JSON 提取。分别覆盖流式/非流式、JSON/文本、reasoning-only、截断和正常内容，保留原有有限重试与失败分类。

### F03 · 资料恢复的临时失败变成永久取消选择

位置：[use-materials.ts](../src/materials/use-materials.ts) L34–61、L176–182；[Home.tsx](../src/pages/Home.tsx) 的发送入口。

恢复逻辑使用 `Promise.allSettled`，只取成功项，然后直接设为 `loaded=true`。资料 GET 失败不会进入外层 `catch`，下一次持久化 effect 就把过滤后的 ID 列表写回 sessionStorage。原选中一份资料、这次请求临时失败时，实际结果为：`files=[]`、持久 ID 列表 `[]`、错误信息为空、`ready=true`。

后端原文件没有被删除；丢失的是首页当前选择及其后续恢复依据。用户可在没有被明确告知的情况下提交不含原资料的路线。收藏夹绑定也采用过滤成功项后保存的模式，恢复状态需要一起处理。

修复建议：把“已选 ID”“已成功加载内容”“恢复失败/待重试”分开保存；未完成恢复时不能覆盖原选择。显式选中而尚未读取的资料应显示失败和重试入口，并阻止忽略该资料发送；只有用户明确移除才修改选择。测试至少覆盖全失败、部分失败、恢复成功、显式移除与账号切换。

### F04 · 全网去重删除了决定文章身份的查询参数

位置：[tools.ts](../server/durable/tools.ts) L175–177；[flows.ts](../server/durable/flows.ts) L59–62。

两个合并入口都先删除 URL 的全部 `search` 与 `hash` 再去重。对路径足以表示内容的链接可能有效，但全网文章可以由 `?id=` 等参数区分。本次 `https://example.invalid/read?id=alpha` 与 `?id=beta` 两条不同证据，经过真实搜索工具后只剩一条。

影响是静默丢失候选文章，使后续筛选与 AI 看不到全部检索证据；不是原 URL 被写成错误链接。修复时应共用来源感知的 URL 规范化方法，只移除已知追踪参数，保留有内容语义的参数。覆盖不同 ID、追踪参数别名、知乎标准链接和跨来源重复证据，不用全域的“去掉查询串”规则。

### F05 · 作者问法校验与真正发出的分组不同

位置：[tools.ts](../server/durable/tools.ts) L33–36、L86–90；[pack-search.ts](../server/agent-runtime/pack-search.ts) L16–45；[flows.ts](../server/durable/flows.ts) L196–202。

`A-card-plan` 的提示词要求每条不超过 90 字，schema 却接受 200 字。结构校验调用共用打包器，三条问法分成 `[第一条+第二条, 第三条]`；实际作者 flow 自己拼成 `[第一条, 第二条+第三条]`。

本次三条长度为 `20 / 150 / 150`，校验侧组合长度为 `171 / 150`，通过项目的 200 字约束；真实发送入口却收到 `20 / 301`。合成搜索边界记录了实际长度，本次没有据此宣称真实知乎已经返回某个错误码。

修复建议：校验与调用共用同一份打包结果，并让 schema 与 90 字合同一致；超过限制时在保存该步骤结果前交回同 Agent 修复。测试两条、三条及边界长度，同时断言三种原问法均被保留。这个问题针对 A-card 分支，不应推导为所有概念搜索都丢了第三问。

### F06 · 合法深层知识树导致布局栈溢出

位置：[tree.ts](../src/learning-v2/tree.ts) L6–20、L42–63；[Graph.tsx](../src/learning-v2/Graph.tsx) L63–69；[learning-v2.ts](../packages/contracts/src/learning-v2.ts) 的树校验。

当前校验逐节点向祖先遍历，长链接近 O(n²)；布局再通过递归 `measure/place` 计算所有节点。测试中的单父无环链全部通过正式合同校验，但当前 Node 运行时的结果是：

| 节点数 | layoutTree 耗时 | 结果 |
| --- | --- | --- |
| 1,000 | 23 ms | 成功 |
| 3,000 | 188 ms | `RangeError: Maximum call stack size exceeded` |
| 6,000 | 891 ms | 同上 |

耗时包含 `layoutTree` 内部校验，不包含前置的独立合同校验。这是一次本机合成长链观测，不代表所有浏览器会在 3,000 个普通节点处失败。实际触发因素是深度；当前服务端节点编辑上限为 20,000，且没有把这样的合法树排除在接口之外。

图组件渲染期间直接调用布局；拖动偏移也在该 memo 的依赖中，会重算基础布局与后代范围。建议先改为迭代后序遍历与线性校验，缓存子节点/后代索引，并将基础布局与拖动偏移分开。随后评估视口裁剪和文档窗口化，保留单父语义。页面级错误边界可在渲染错误时提供恢复入口，但不能替代布局修复；React 的错误边界机制见[官方文档](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary)。

## 3. AI 后端及平台优化建议

以下属于源码支持的优化方向，除注明的构建体积与布局复现外，本轮没有测出生产性能收益，不应写成已发生的线上事故。

### O1 · 按实际目标 provider 分配上下文预算

[bootstrap.ts](../server/durable/bootstrap.ts) 从 `DEEPSEEK_CONTEXT_TOKENS` 建立一个 `window`，而 [tools.ts](../server/durable/tools.ts) 的结构化模型与知乎直答都使用它压缩上下文。当前已有输出预留、安全余量与业务上限，不能说所有调用都固定塞入 500k；不足之处是不同服务缺少独立能力配置。

建议建立按 provider、模型和调用类型选择的能力记录：输入窗口、最大输出、深度额外预留、token 估算方法及依据日期。知乎直答与 DeepSeek 分别校验，网关模型必须显式配置。用“小窗口直答 + 大窗口规划”的组合测试验证每个请求。没有本轮真实知乎窗口和 usage 测量，暂不认定现在一定超窗。

### O2 · 减少反复压缩，同时补齐摘要版本身份

[context.ts](../server/durable/context.ts) 已按来源分块、有目标/用途输入、保留原文并缓存摘要；每份摘要最多多轮缩减，`packContext` 还可能继续压缩已压缩的字段。长材料冷启动可能需要较多串行模型调用，不能只统计最终 Agent 的生成时间。

建议记录每一步输入估算/实际 token、摘要调用次数、分块数、压缩耗时和缓存命中；先测冷启动，再考虑同来源分块的有限并发、稳定顺序合并、按预算档位复用。不得丢分块或取消首次学习的三种角度。摘要缓存当前包含所有者隔离、合同版本、来源、文本、用途、预算和深度，建议再纳入真实模型/服务命名空间及压缩策略身份，避免切换模型后无法区分旧摘要质量。

### O3 · 把过期记录清理移出每次 provider 请求

[provider-runtime.ts](../server/durable/provider-runtime.ts) 在成功直答缓存写入事务中删除全部到期缓存，在每次记录调用后删除全部超过 7 天的调用记录；业务路径等待这些数据库操作。随着过期记录规模增长，清理可能与当前请求争用数据库资源。

已有 [store.ts](../server/durable/store.ts) 的批量维护框架，可以把这些已定义 TTL 的清理纳入有界批次，记录耗时与积压。缓存有 `expires_at` 索引；调用日志有 `(owner_id, created_at)` 索引，不能笼统说没有索引。全局按时间删除的执行计划仍须在真实 PostgreSQL 上用代表性数据检查，再决定是否增建时间索引；多列 B-tree 的效果取决于约束列和数据分布，参见[PostgreSQL 文档](https://www.postgresql.org/docs/current/indexes-multicolumn.html)。不应顺带删除没有过期策略的用户资料或摘要。

### O4 · 为资料库与作者网络建立较轻的读取路径

[store.ts](../server/durable/store.ts) 的 `list` 没有分页、读取完整 resource；[http.ts](../server/durable/http.ts) 的资料库入口先取全量路线、学习和聊天，再投影目录信息。`snapshot` 也从数据库读取完整最新 job，包括未提供给 UI 的输入和检查点，最后才转成 `jobView`。

[authors-network.ts](../server/durable/authors-network.ts) 会读取该所有者的学习、路线、资料、偏好与使用记录，`sourceForNode` 又在多次逐节点调用时重建节点 Map、扫描文章或对话。在长期学习数据下，这是值得优先测量的读取成本。

建议目录分页、只查询需要的 JSON 字段、给任务视图裁剪数据库列；先一次构建节点、文章、对话段落索引，再考虑按资源 revision 缓存或增量维护作者来源读模型。更新/删除卡片和撤销反馈必须同步失效，多作者、多文章、多问题、多概念关系不能被压成单父树。用真实 PostgreSQL 的查询耗时、传输字节和 P95 验证，不能仅凭 SQL 形状宣称目前数据库已经慢。

## 4. 前端与工程优化建议

### O5 · 统一条件轮询和编辑增量，保留恢复能力

[Workspace.tsx](../src/learning-v2/Workspace.tsx) 已用 revision 避免无变化时传输完整资源；[OrdinaryChat.tsx](../src/learning-v2/OrdinaryChat.tsx) 仍持续读取完整快照，完成后也没有退出轮询。普通聊天可复用条件读取，空闲或隐藏时降低频率，发送、恢复和重新聚焦时及时刷新，保留跨设备变化的发现能力。

学习页编辑每次发送 `nodes + baseNodes + revision`，并持有最多 40 份撤销历史。大树编辑会放大内存、序列化和传输成本。先测规模，再设计按节点的增量补丁与历史操作；必须保留当前三方合并、冲突提示、未保存内容恢复和服务端校验，不能用“最后一次写入覆盖”简化并发语义。

### O6 · 根据实际页面测量重渲染与分包

本次构建的部分压缩后 JS 文件大小如下。它们是不同加载时机的 chunk，不能相加当作首页初始下载量。

| chunk | 文件体积 | gzip |
| --- | --- | --- |
| main | 378.49 kB | 136.52 kB |
| Home | 151.11 kB | 54.20 kB |
| MarkdownMath | 440.67 kB | 133.85 kB |
| shelf-scene | 533.37 kB | 134.89 kB |
